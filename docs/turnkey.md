# 턴키 실행·재개 계약

이 프로젝트의 턴키 실행기는 **고정된 로컬 자동 검증을 실행하고 그 증거를 남기는 도구**입니다. 프롬프트를 자의적으로 셸 명령으로 바꾸거나, LLM을 호출하거나, 권한을 우회하지 않습니다. 문서 작성·설치·Figma 작업·공개 출시·고객 조사까지 자동 완료 처리하지 않습니다.

## 실행 명령

```powershell
npm run turnkey -- check
npm run turnkey -- --next
npm run turnkey -- --resume
npm run turnkey -- status
npm run turnkey -- --help
```

npm이 PATH에 없으면 Node 24 실행파일로 `scripts/turnkey.mjs`에 같은 인수를 전달합니다. 실행기는 npm을 다시 호출하지 않으며 현재 Node 실행파일로 설치된 TypeScript, Node 테스트 러너, Vite를 실행합니다. 의존성 설치는 별도 준비 작업입니다.

| 명령 | 동작 |
| --- | --- |
| `check` 또는 `--check` | 새 실행 원장으로 전체 자동 검증 시작 |
| `next` 또는 `--next` | 현재 입력에서 첫 미통과 단계 하나 실행 |
| `resume` 또는 `--resume` | 현재 입력에서 첫 미통과 단계부터 순차 재개 |
| `status` | 최신 원장과 현재 입력의 일치 여부 표시 |
| `help` 또는 `--help` | 도움말 출력 |

자동 순서는 Node 24+/SQLite 사용 가능 여부 → 필요한 로컬 패키지 존재 → TypeScript → SQLite API 테스트 → PostgreSQL API 테스트 → Vite 빌드입니다. PostgreSQL 시험은 메모리 내 격리 DB를 사용하며 원격 DB 설정을 읽지 않습니다. 명령 종료 코드가 0인 경우만 해당 검증을 `PASS`로 기록합니다. 의존성 검사 통과는 설치 작업을 수행했다는 뜻이 아닙니다.

## 증거와 재개

- 원장: `reports/turnkey/ledger.json`.
- 로그: `reports/turnkey/<run>-<step>-<attempt>.log`. 실행 인수, 시각, 출력, 종료 코드가 남습니다.
- 상태: `PENDING`, `RUNNING`, `PASS`, `FAIL`, `BLOCKED`.
- `src`, `server`, `tests`, `scripts`, `public`, 패키지·잠금·빌드 설정·개발 계약과 Node 환경의 SHA-256 지문이 달라지면 새 검증을 시작합니다. `pnpm-workspace.yaml`, `.npmrc`, `Start-KJ-Trail.ps1`, `Start-KJ-Trail.cmd`, pnpm 설치 메타데이터와 주요 직접 의존성의 설치된 package.json도 포함합니다.
- 검증 중 입력이 바뀌면 원장을 오래된 결과로 표시합니다. 기존 통과를 현재 코드의 통과로 재사용하지 않습니다.
- 테스트 실패 시 이후 단계는 미실행 상태로 유지합니다. 수정 후 재개 명령을 실행합니다. 입력이 바뀌었다면 선행 검사부터 다시 수행합니다.
- 종료 코드를 기록하지 못한 중단 단계는 재개 시 통과가 아니라 `BLOCKED`입니다. 동시에 두 실행기가 원장을 쓰지 않도록 프로세스 잠금을 둡니다.
- 검증 하나의 제한 시간은 5분입니다. 제한 시간이나 사용자 중단은 실패 원인으로 기록되며 완료로 처리하지 않습니다.
- 실행기나 원장에 임의의 명령을 넣어 실행시키는 옵션은 없습니다. 로그·DB·보고서는 Git에서 제외됩니다.

출력은 단계 실행 중 로그에 바로 추가하므로 강제 종료 전까지 받은 출력도 남습니다. 설치된 모든 전이 의존성 파일의 무결성을 검사하는 도구는 아닙니다. 의존성 파일을 직접 수정했거나 설치 상태가 의심되면 잠금파일에 맞게 설치를 복구한 뒤 `check`로 새로 검증합니다.

### 강제 종료 후 잠금 복구

정상 종료·검증 실패·일반 중단은 잠금을 해제합니다. PC 종료나 실행기를 강제 종료한 경우에는 `reports/turnkey/.lock`이 남을 수 있습니다. 동시 재개가 서로의 잠금을 삭제하지 않도록 죽은 PID의 잠금도 자동 삭제하지 않습니다.

먼저 잠금의 `owner.json`에 기록된 PID와 실행기에서 시작된 검증 프로세스가 모두 종료되었는지 확인합니다. 새 검증을 동시에 시작하지 않는 상태에서 프로젝트 폴더의 아래 **두 알려진 항목만** 정리한 뒤 `--resume`을 실행합니다. 원장·로그·DB는 지우지 않습니다. 실행 중인지 불명확하면 정리하지 않습니다.

```powershell
Get-Content -LiteralPath .\reports\turnkey\.lock\owner.json
# 기록된 실행기와 자식 검증 프로세스가 모두 종료된 것을 확인한 뒤에만:
Remove-Item -LiteralPath .\reports\turnkey\.lock\owner.json
Remove-Item -LiteralPath .\reports\turnkey\.lock
npm run turnkey -- --resume
```

원장은 자동 시험의 증거입니다. 실제 사람의 언어 검토, 현장 확인, 자산 권리, 실기기 사용성, 운영 책임, 호스팅, 복구 훈련은 [수용 기준](acceptance.md)과 [운영 절차](operations.md)에 별도로 기록합니다.

## 13개 프롬프트의 실제 의존 순서

원문은 [실행 프롬프트 13종](original-execution-prompts.md)에 보존했습니다. 장 번호는 작업 분류이며 단순 번호순 실행을 뜻하지 않습니다. 이번 구현의 API 정본은 [API-CONTRACT.md](../API-CONTRACT.md)입니다.

| 실행 묶음 | 사용하는 카드 | 산출물·인계 조건 |
| --- | --- | --- |
| 1. 착수·기반 | P00, P01 | 고객 과업·결정 장부, 실제 실행 환경, fixture/운영 데이터 경계 |
| 2. 계약·와이어프레임 | P02, P03, P06, P08, P09의 계약 부분 | 인증·역할·콘텐츠 상태·메시지·신고·감사 계약을 먼저 고정. 화면 상태와 대응 |
| 3. 인증·콘텐츠·운영 코어 | P06, P03, P09 서버 부분 | 실제 세션·DB, 콘텐츠 공개/추천 판정, 신고·제재·잠금·감사 기능 |
| 4. 사용자 과업 | P04, P05, P07, P08, P09 화면 부분 | 코스 탐색·추천, 현지화, 게시판·채팅, 관리 화면을 같은 계약에 연결 |
| 5. 공동 통합 QA | P10 + P08/P09 | 두 계정 채팅→신고→숨김/복구→감사, 권한 회수·오류·재접속을 함께 검증 |
| 6. 실제 사용의 개선 | P11 | 실제 배포 버전·기간·관찰/운영 근거가 있어야 분석. 없으면 `BLOCKED_NO_EVIDENCE` |
| 7. MVP2 판단 | P12 | P11 근거에 기반한 최소 개선·호환성·운영 비용 검토. 근거 없으면 `BLOCKED_NO_EVIDENCE` |

P03이 승인 상태·추천 자격의 정본을 소유하고 P09는 이를 사용하는 운영 기능을 구현합니다. P09의 신고·제재 서버 계약을 P07/P08보다 먼저 정의하므로 채팅과 관리자 사이의 순환을 피합니다. 현지화·접근성·콘텐츠 검토는 마지막에만 수행하지 않고 각 기능 묶음에서 반복합니다.

## 현재 구현에 적용하는 차이

- Node HTTP 서버와 자체 회원·세션 인증을 사용합니다. `DATABASE_URL`이 있으면 Supabase PostgreSQL, 없으면 SQLite에 저장합니다. 서버의 기본 접속 범위는 이 PC이며 공개 호스팅은 별도입니다.
- 채팅은 현재 참여 권한을 매 요청마다 검사하는 3초 폴링과 제한된 전체 스냅샷을 사용합니다. WebSocket·푸시 알림·무한 대화 이력 동기화를 구현했다고 주장하지 않습니다.
- 원본 프롬프트의 호스팅·소켓 검증은 해당 기능이 추가될 때 검수해야 할 후속 조건입니다.
- Figma 파일 저장·브랜드 최종 승인·외부 앱 자동 연동은 코드 빌드 성공으로 증명되지 않습니다.
- 공개 출시는 [수용 기준](acceptance.md)의 별도 운영 조건을 충족해야 합니다. 자동 검증 성공은 공개 출시 승인 또는 배포 기록이 아닙니다.
- P11/P12의 상태는 이 실행기에서 자동으로 통과시키지 않습니다. 실제 근거와 담당 검토 기록은 [피드백 절차](feedback.md)에 남깁니다.

[Claude 교차 검토 원문](claude-turnkey-review.md)은 제안·한계를 보존한 자료입니다. 원문의 일괄 외부 작업 금지, 반복 승인 강제, 고정 재시도 횟수 등의 제안은 이번 실행기의 정책으로 자동 채택하지 않았습니다. 실제 사용자 승인 범위와 현재 프로젝트 계약을 따릅니다.
