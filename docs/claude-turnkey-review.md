# KJ Trail 실행 프롬프트·관리자 명세 교차 검토 (Claude)

검토 대상은 붙여 주신 텍스트뿐입니다. 저장소, Notion, Figma, Supabase를 열어 보지 않았고 실행이나 테스트도 하지 않았습니다. 이 세션의 작업 폴더가 git 저장소가 아니라는 점만 환경 정보로 알고 있습니다. 아래 수정안은 모두 제안이며 승인된 정책이 아닙니다.

## 1. 치명도별 발견

처리 규칙(제안): 치명은 엔진 실행 전, 높음은 해당 노드 시작 전, 중간은 해당 노드 완료 전에 수정합니다. 낮음은 기회가 있을 때 고칩니다.

| ID | 치명도 | 문제 | 미수정 시 결과 |
|---|---|---|---|
| C1 | 치명 | 번호순이 의존성과 맞지 않습니다. P08은 "P09와 함께 검증"인데 P09가 뒤에 있습니다. P07·P08이 쓸 신고/잠금 훅이 P09에 있습니다. 코스 승인 상태기계가 P03과 P09에 중복됩니다. P02(최종 화면)가 계약(P03/P06)보다 앞입니다. | 엔진이 스텁으로 "공동 검증"을 보고하거나 교착됩니다. |
| C2 | 치명 | 턴키 실행 장치가 없습니다. 머리말은 사람이 카드를 하나씩 붙이는 수동 절차인데, 승인 사항은 서브에이전트와 자동 검수입니다. 실행 원장, 상태 코드, 재개 규칙, 재시도 한도, 멱등성 규칙이 없습니다. | 중단 후 재개 시 마이그레이션 중복과 덮어쓰기가 생기고, 같은 노드가 실행마다 다르게 "완료"로 판정됩니다. |
| C3 | 치명 | 완료 판정이 자기 보고입니다. 작성 엔진이 테스트도 만들고 결과도 보고합니다. "독립 검토 여부" 칸만 있고 독립의 조건이 없습니다. "원본 결과"는 요구하지만 보존 위치와 재현 규칙이 없습니다. | 인증, 채팅, 관리자 권한에서 오판 통과나 날조가 생깁니다. |
| C4 | 치명 | 외부 행위 경계가 모호합니다. P10의 "현재 승인 범위에 맞춰 배포하고", 머리말의 "비밀키를 임의로 선택하지 말고", P11의 "수정 PR→배포"가 그렇습니다. P01은 저장소를 만들지 클론할지도 정하지 않았습니다. | 무승인 호스팅 생성, 원격 푸시, 공개가 일어날 수 있습니다. |
| C5 | 치명 | P11에만 "자료가 없으면 준비 단계" 가드가 있고 P12에는 없습니다. 번호순 자동 실행이면 P12가 이어집니다. | 근거 없는 MVP2 백로그나 가상 성과가 만들어집니다. |
| C6 | 치명 | 미정 정책 처리가 "확정된 부분만 구현"뿐입니다. 미설정 상태를 코드로 표현하는 방법이 없습니다. | 엔진이 보존 기간, 이력 범위, 신선도 기한을 임의로 정하거나 프롬프트 전체가 멈춥니다. |
| H1 | 높음 | P09가 백엔드, 프론트, 전 메뉴를 한 번에 요구합니다. | 실패 후 재개가 불가능하고 컨텍스트가 초과됩니다. |

| H5 | 높음 | P10이 마지막 단일 게이트입니다. 합의한 슬라이스·독립 검토 워크플로와 모순되는 사실상 워터폴입니다. | 후반에 결함이 몰립니다. |

| M1 | 중간 | 역할표는 콘텐츠 담당에게 편집과 승인을 묶었는데, 본문은 분리 여부를 미정이라고 합니다. | 권한 모델이 나중에 깨집니다. |
| M2 | 중간 | "최대 3개 결과" 같은 수치는 승인된 값이 아닙니다. | 하드코딩됩니다. |
| M3 | 중간 | 자동화 불가 기준(관리자 완료 기준 8번, 실기기, 언어 검수)이 자동 검증 기준과 한 목록에 섞여 있습니다. | 엔진이 사람 확인을 건너뜁니다. |
| M4 | 중간 | 번역 상태 소유가 P03, P05, P09에 걸쳐 있습니다. | 상태가 둘 이상 생깁니다. |
| M5 | 중간 | 보존·삭제 시험이 P10에 없습니다. | 정책 미정이라 빠진 것인지 누락인지 구분되지 않습니다. |
| L1 | 낮음 | BOT-LEGACY를 입력에서 제외한다는 문구가 없습니다. "원본 코드가 있으면 존중"은 레거시 이관으로 읽힐 수 있습니다. | 사용자 정정과 충돌합니다. |

## 2. 순환·선행 역전 요약

1. P02(최종 화면)와 P03/P06(계약)이 서로를 필요로 합니다.
2. P03(승인 상태)과 P09(승인 UI)가 같은 상태기계를 각각 정의합니다.
3. P07/P08은 신고·잠금 훅이 필요하고, P09는 채팅 조치 대상(P08)이 필요합니다.
4. P08 실행 시점에는 P09가 없으므로 "함께 검증"을 만족할 수 없습니다.
5. P00은 시작 문서인데, Supabase와 Figma 확인 결과를 P01 이후에 갱신해야 하므로 "살아 있는 장부"여야 합니다.

## 3. 제안 DAG (P03/P06/P09 분리)

`a`는 계약(DB와 호스팅 불필요), `b`는 로컬 또는 mock 어댑터 대상 구현, `c`는 실제 환경 통합입니다.

```
P00 ─┬─ P01
     ├─ P02a(와이어프레임) ─────────────────────────┐
     ├─ P03a ─┐                                      │
     ├─ P06a ─┼─ P08a ─┐                             ├─ P02b(상태 바인딩, 최종 토큰은 D-design 후)
     └─ P09a ─┘        │                             │
P03b ← P01,P03a   P06b ← P01,P06a   P09b1(모더레이션 코어) ← P06b,P09a
P09b2(콘텐츠·번역·관리자 UI) ← P09b1,P03b,P02b
P04 ← P03b,P02b   P05 ← P02b,P03a   P07 ← P06b,P09b1   P08b ← P08a,P06b,P09b1
통합(결정 필요): P03c ← P03b+D-host │ P06c ← P06b+D-host+D-auth │ J-CHAT(P08c+P09c) ← P08b,P09b1,P06c
P10-RC ← 위 전부 │ 사용자 go/no-go(자동 아님) │ P11 ← 실제 파일럿 증거 │ P12 ← P11
```

| 노드 | 산출 | 판정 유형 |
|---|---|---|
| P03a | 코스/출처/증거/공지/번역 스키마, 승인 상태기계(정본), 추천 적격성 규칙 명세, 가상 fixture | AUTO |
| P03b | 마이그레이션, 조회·게시 함수, 순수 적격성 함수, 단위·계약 테스트 | AUTO(로컬/격리 DB), 환경 없으면 BLOCKED_ENV |
| P03c | 실제 프로젝트에 적용하고 계약 테스트 재실행 | DECISION(호스팅) |
| P06a | 역할·권한 매트릭스, 방 참여 기간 모델, 오류 코드, 세션 회수 의미, 권한 테스트 명세 | AUTO |
| P06b | 인가 함수와 어댑터, 부트스트랩 관리자 절차, mock 인증 기반 테스트 | AUTO(MOCK_VERIFIED까지) |
| P06c | 실제 인증 제공자로 직접 API 남용, 세션 회수 시험 | DECISION |
| P09a | 신고, 조치, 제재, 방 잠금, 감사 레코드, 편집/승인 권한 분리, 상태기계 | AUTO |
| P09b1 | 모더레이션 서버 코어(감사 기록과 같은 트랜잭션) | AUTO |
| P09b2 | 코스·출처·번역 관리, 관리자 UI | AUTO + 시각 검수 HUMAN |
| J-CHAT | 두 실제 계정: 신고→숨김→복구→감사, 제재·잠금·회수 후 기존 소켓 차단 | DECISION(호스팅·인증) 후 AUTO |

## 4. 구현 엔진 전달 교정문

### A. 공통 머리말 교체본

```text
[실행 규칙 v2 — 제안, 사용자 승인 정책 아님]
1. 입력: 저장소의 docs/·contracts/·policy/ 파일만 정본으로 읽어라. Notion 등 외부 링크는 접근 성공 시에만 참고하고, 접근 실패나 내용 불일치는 BLOCKED_ENV로 기록하라. 추정으로 채우지 마라.
2. 원장: docs/ops/run-ledger에 노드별 {상태, 입력 계약 버전, 브랜치/워크트리, 시작·종료 커밋, 마지막 명령, 실패 사유, 재시도 횟수, 증거 경로}를 기록하라. 시작 시 원장을 먼저 읽어 이미 검증된 노드는 입력 버전이 같으면 건너뛰고, 선행 계약 버전이 바뀌었으면 재실행하라. 이미 존재하는 마이그레이션·파일을 덮어쓰지 말고 추가 변경으로 처리하라.
3. 상태: NOT_STARTED / IN_PROGRESS / BLOCKED_DECISION(결정ID) / BLOCKED_ENV / BLOCKED_NO_EVIDENCE / IMPLEMENTED_UNVERIFIED / MOCK_VERIFIED / AUTO_VERIFIED / HUMAN_REQUIRED. 엔진은 AUTO_VERIFIED까지만 설정할 수 있고 ACCEPTED는 사용자만 부여한다. mock 결과는 MOCK_VERIFIED를 넘지 못한다.
4. 스케줄: 모든 선행 노드가 AUTO_VERIFIED이거나 해당 계약이 확정된 노드만 시작하라. 막힌 노드는 사유 코드와 함께 남기고 독립 노드를 계속하라.
5. 재시도: 같은 실패는 대상을 좁힌 수정으로 최대 2회(제안값) 시도하고, 이후 BLOCKED로 기록하라. 시험을 약화·삭제하거나 건너뛰어 통과시키지 마라.
6. 증거: 명령, 종료 코드, 전체 stdout/stderr, 환경 버전, 커밋 SHA를 evidence/<노드>/<SHA>/에 저장하라. 비밀값과 개인정보는 제외하라. 요약문은 증거가 아니다.
7. 독립성: 인증·권한·채팅·모더레이션·추천 적격성은 (a) 계약만 보고 시험 명세를 쓰는 서브에이전트, (b) 구현 서브에이전트, (c) diff·계약·증거만 받아 클린 체크아웃에서 명령을 재실행하는 읽기 전용 검토 서브에이전트를 분리하라. 작성자의 설명은 검토자에게 전달하지 마라. 이는 AI 자동 검수이며 사람 QA를 대체하지 않는다. 보고서에 그렇게 적어라.
8. 외부 행위 금지(별도 결정 기록이 있을 때만 허용): 호스팅/DB 프로젝트 생성, 결제 설정, 실제 비밀키 생성·저장, 원격 푸시·PR, 프리뷰/프로덕션 배포, 도메인·공개 설정. 로컬 파일, 로컬 커밋, 로컬 격리 DB는 허용한다. 공개 출시는 어떤 노드도 수행하지 않는다.
9. 정책: policy/에 키별 {PROPOSED | UNSET | APPROVED}를 두고, 코드는 값을 하드코딩하지 말고 설정에서 읽어라. 릴리스 프로필은 필수 키가 APPROVED가 아니면 빌드·점검 실패. 개발/시험 프로필은 TEST_ONLY 값을 허용하되 화면에 표시하라.
10. 콘텐츠: 실제 금정산 사실을 기억이나 웹에서 채우지 마라. 외부 사이트 문구를 가져오지 마라. data_origin(fixture|draft|approved)을 모든 코스 레코드에 두고, fixture는 릴리스 프로필에서 노출되면 실패하도록 시험하라. 엔진이 작성한 번역은 machine_unreviewed로만 표시하라.
11. BOT-LEGACY-P1..7과 기존 레거시 코드를 입력으로 쓰거나 이관하지 마라.
12. 완료 보고는 상태 코드, 증거 경로, HUMAN_REQUIRED 목록, 미결 결정ID를 포함하라.
```

### B. 노드별 패치

```text
[P00] 장부를 일회성 작성이 아닌 갱신 문서로 만들어라. 각 노드가 발견한 사실(연결 상태, 파일 존재 여부)을 장부에 반영하라. 확인하지 못한 서비스는 "미확인"으로 남겨라. 작업 폴더가 git 저장소가 아니면 저장소 부트스트랩 방식(클론/초기화)을 결정 항목으로 올려라.
[P01] 로컬 git init과 로컬 커밋까지 수행하라. 원격 연결은 결정 기록이 있을 때만. 레거시 코드 이관을 목적으로 하지 마라.
[P02] P02a는 와이어프레임과 상태 목록(정상/로딩/빈/오류/권한/오프라인)까지만. 최종 시각 토큰은 디자인 기준 결정 전까지 적용하지 마라. P02b는 P03a·P06a·P08a·P09a 계약을 화면 상태에 바인딩하라.
[P03] 승인 상태기계와 추천 자격은 P03a에서 한 번만 정의하고 P09는 이를 호출만 하라. 갱신 기준은 데이터 유형별 정책 키로 읽고, 키가 UNSET이면 능동 추천 대상이 비어 있음을 정상 동작으로 처리하라(허용 오류 아님). 조회 실패를 통제 없음으로 변환하지 마라.
[P04] "최대 3개" 등 수치는 설정값(TEST_ONLY 표기)으로 읽어라. 추천 적격성은 UI·LLM과 독립된 순수 함수로 시험하라. 적격 0건과 출처 충돌 시험을 포함하라.
[P06] 방 참여는 시각 하나가 아닌 참여 기간 레코드(시작/종료/상태)로 저장하라. 이력 범위·재참여 처리는 이 레코드에서 계산하는 정책 함수로 분리하라. 기본 동작은 개발/시험 프로필에서만 "참여 시각 이후"(PROPOSED)로 두고 릴리스는 APPROVED 필요. 첫 관리자는 1회성 부트스트랩 절차(시크릿은 환경에서만, 사용 후 비활성, 감사 기록)로 만들고 시험하라.
[P07] 신고 진입점은 P09a의 신고 계약만 호출하라. 신고 처리 로직을 구현하지 마라.
[P08] P08a(계약)에 메시지, 알림 페이로드(본문·작성자 없음), 커서, 멱등 키, 오류, 가시성 필터 인터페이스를 정의하라. 차단/뮤트는 인터페이스 자리만 두고 동작은 구현하지 마라(D-block 미정). mock 인증의 두 계정 시험은 MOCK_VERIFIED. 실제 소켓·세션 회수 시험은 J-CHAT 이후에만 AUTO_VERIFIED.
[P09] 모더레이션 코어(신고·조치·제재·잠금·감사)를 UI와 분리해 먼저 구현하라. 조치와 감사 기록은 같은 트랜잭션으로, 감사 기록은 일반 권한에서 수정/삭제 불가를 DB 수준으로 시험하라. 편집과 승인은 별도 capability로 구현하고 역할은 설정으로 묶어라.
[P10] 배포를 수행하지 마라. 노드별 게이트 결과를 모아 출시 후보 판정서(통과/실패/미검증/해당 없음+사유)만 작성하라. 프리뷰 배포는 호스팅 결정 기록이 있을 때 별도 승인 후에만. 보존·삭제 시험은 정책 UNSET이면 "해당 없음(D-retention)"으로 표기하라.
[P11] 실제 배포 버전 ID, 관찰 기간, 이벤트 사전 버전, 분모가 있는 집계 증거가 evidence/pilot/에 없으면 BLOCKED_NO_EVIDENCE로 종료하고 이벤트 사전·피드백 카드 양식·계측 점검표만 산출하라. 수치, 인용, 고객 발견, 만족 여부를 만들지 마라. PR 생성·배포를 수행하지 마라.
[P12] P11이 AUTO_VERIFIED가 아니면 실행하지 마라(BLOCKED_NO_EVIDENCE). 증거가 있어도 후보는 "관찰 근거/출처/한계"를 필수로 하고, P10 QA에서 나온 기술 결함은 고객 근거와 구분하여 표시하라.
```

### C. 관리자 명세 수정 제안

- **MVP1 최소 메뉴(제안)**: 코스·출처, 번역, 공지·현재 상태, 신고, 회원·방, 감사 기록. 자산, 현황 지표, 신고자 상태 알림, 운영 안내·설정은 MVP1 사진/업로드 범위와 데이터 소스가 결정될 때까지 보류합니다. 이의제기는 신고 레코드의 메모 필드로 대체합니다. 보류하려면 사용자 결정이 필요합니다.
- **권한**: 역할표의 "편집/승인"을 capability 둘로 분리합니다. 역할 묶음은 설정으로 둡니다.
- **완료 기준 8개의 유형**:
  - 1, 2, 3, 4, 5는 AUTO입니다. 5는 J-CHAT 통합 후에만 가능합니다.
  - 6은 실제 인증 제공자가 있어야 하므로 P06c 이후입니다.
  - 7은 실제 쿼리가 있는 지표만 대상이며, 나머지는 "미연결" 표시를 확인합니다.
  - 8은 HUMAN_REQUIRED입니다. 엔진이 달성할 수 없습니다.
- **차단**: 의미는 정책이 확정될 때까지 구현하지 않고 인터페이스만 둡니다(H2).

## 5. 한계와 남는 판단

- 엔진·서브에이전트가 실제로 이 원장 방식과 독립 검토 분리를 지킬지는 이 텍스트만으로 판단할 수 없습니다. 첫 실행에서 원장과 증거 파일이 실제로 생성되는지 확인해야 합니다.
- 재시도 한도 2회, 상태 코드 이름, 증거 경로는 제 제안이며 합의된 값이 아닙니다.
- AI 검토 서브에이전트의 재실행은 작성자 자기 보고보다 낫지만 사람 QA와 같지 않습니다. 인증·채팅·관리자는 `HUMAN_REQUIRED`로 최소 한 번 사람이 증거를 보는 지점을 두길 권합니다.
- 호스팅·인증 결정(D-host, D-auth)과 디자인 기준 결정(D-design)이 없으면 통합 노드와 최종 시각 작업은 시작되지 않는 것이 정상 동작입니다.
